# ADR: WebMCP採用の是非(2026-09-22)

Status: 不採用(現状維持。`window.EbookMaker` + `llms.txt` を継続)
関連: `src/lib/automationApi.ts`、`public/llms.txt`

## 背景
ebook-makerは`src/lib/automationApi.ts`で`window.EbookMaker`(`describe()`/`getState()`/`importFiles()`等)を公開し、`public/llms.txt`でその使い方をエージェント向けに文書化している。ブラウザを直接操作できるエージェント(例: Claude in Chrome、Playwright駆動のボット)は、DOM操作の代わりにこのAPIを直接呼び出して画像の読み込み・並べ替え・調整・書き出しを行える。

一方「WebMCP」は、Webページが自身のツールをMCP互換の形式で宣言的に登録し、ブラウザ/ブラウザ拡張機能が標準的な手段でそれを発見・呼び出せるようにする**策定中の提案**(例: MCP-Bのような拡張機能実装)。目的は「サイトごとに独自のAPI仕様書(`llms.txt`等)をエージェントに読ませる」のではなく、「ツール定義自体をページから機械可読な形で公開し、ブラウザ側のAIが自動発見する」こと。この採否を検討した。

## 判断
WebMCPが本当に価値を持つのは、エージェント側がそのサイト固有のドキュメント(`llms.txt`等)を読まなくても、ページ自身がツールを申告してきて**汎用ブラウザ内AIが自動発見する**シナリオ。今このプロジェクトが対象にしているのは、Claude in Chromeのように**任意のJSを実行できるエージェント**であり、これは`describe()`を一度呼べば自己文書化されたAPIを読み取れるため、WebMCPが解決する問題を実質的に先取りして解決済みと言える。

加えてWebMCPはまだ標準化の初期段階で、主要ブラウザへの正式なネイティブ実装がない(実験的な拡張機能やベンダーの提案止まり)。今作り込むと仕様変更で書き直しが発生するリスクが高く、コストに見合わない。クライアントサイド完結・サーバーレスという設計思想上、WebMCPの実装例の多くが前提とする「拡張機能/ブラウザ側ランタイム」への依存が増えるのもこのプロジェクトの性質と噛み合わない。

| 案 | 標準化状況 | 対応エージェント | 実装コスト | 評価 |
|---|---|---|---|---|
| A. 現状維持(`window.EbookMaker` + `llms.txt`) | サイト固有の素朴なJS API | JSを直接評価できるものすべて(Claude in Chrome, Playwright等) | ゼロ(既存) | **採用**。現在の主要ユースケースを既に満たしている |
| B. WebMCPを既存APIと併用導入 | ドラフト段階、主要ブラウザに正式実装なし | WebMCP対応クライアント(現状ごく限定的)のみ恩恵 | 中〜高。仕様追従のため二重管理になる | 不採用(時期尚早) |
| C. WebMCPへ全面置き換え | 同上 | 同上 | 高、可用性リスクあり | 却下 |

## 結論
現時点ではWebMCPへの移行・追加実装は行わない。既存の`window.EbookMaker` + `llms.txt`を維持する。

将来のための布石として、`AutomationApiDescription`の`methods`をより構造化されたスキーマ(引数の型情報をJSON Schemaで持つ等)にしておくと、仕様確定後にWebMCP対応する際の移行コストを下げられる(今すぐやる必要はない)。

## 再評価のトリガー
WebMCP/MCP-Bがブラウザベンダーの正式サポートを得た、またはClaude in Chromeのようなエージェントが標準的なツール発見を要求するようになった時点で再検討する。
